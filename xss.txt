Stored XSS in file upload

Type: Stored XSS
Severity: High
Target: http://10.0.1.11/api/files and http://10.0.1.11/api/files/{id}

Account: Any account. A free account can be made at http://10.0.1.11/.

How the URLs were found

A port scan of the target network found a web server at http://10.0.1.11/.

Opening http://10.0.1.11/ shows a file sharing site named fileshares.kz.

The Open your workspace button opens a login form. The Create account tab makes a new account. After signup, the site logs the user in.

DevTools (F12) then Network tab shows the upload request: POST /api/files.

The request sends the file and a visibility value. The response is JSON:

{"file":{"id":124,"owner_id":48,"name":"xss.html","mime":"text/html","visibility":"public","privateHash":null}}

The site shows a Download file link. Its address is /api/files/124.

Opening that address directly returns the file. The Content-Type in the response is the same as the file's mime field.

What the bug is

The server saves the Content-Type the client sends. It uses that same Content-Type later when serving the file.

The server does not check the file type. It does not stop HTML files.

HTML files are served with Content-Disposition: inline. This tells the browser to show the file as a page, not download it.

So an HTML file with JavaScript inside runs when someone opens the file URL. The JavaScript runs on the fileshares.kz origin. This is stored XSS.

Steps to reproduce

All steps are done in Firefox.

Step 1 - make an account.

Open http://10.0.1.11/. Click Open your workspace. Click Create account. Type any username and password. Submit. The site logs the user in.

Step 2 - make a bad file.

Create a file called xss.html on the local machine. Put this inside:

<script>alert(document.domain)</script>

Step 3 - upload the file.

On the workspace page, click Choose a file. Pick xss.html. Set it to Public. Click Upload file.

Open DevTools (F12). Click Network. Click the POST /api/files request. The response contains the file id. In this example the id is 124.

Step 4 - find the direct URL.

The public page is http://10.0.1.11/files/public/124.

The Download file button links to http://10.0.1.11/api/files/124.

Step 5 - run the JavaScript.

Open a new tab. Type http://10.0.1.11/api/files/124. Press Enter.

An alert box appears. It says 10.0.1.11. The JavaScript ran on the site's origin.

Step 6 - check it is stored, not reflected.

Open a new Private Window in Firefox (Ctrl+Shift+P). Do not log in.

Open the same URL: http://10.0.1.11/api/files/124.

The alert appears again. The JavaScript is saved on the server. Anyone who opens the URL runs it.

Screenshots

1. DevTools then Network. The POST /api/files request. The response shows "mime":"text/html" and the file id 124.

2. DevTools then Network. The GET /api/files/124 request. The response headers show:

content-type: text/html; charset=utf-8
content-disposition: inline; filename="xss.html"

3. The address bar with http://10.0.1.11/api/files/124 and the alert box.

4. A Private Window with the same URL and the same alert. This proves the XSS is stored.

5. DevTools then Console. Run document.cookie. It returns empty. This shows the cookie is HttpOnly.

Impact

Anyone who opens a bad file URL runs the attacker's JavaScript on the site's origin.

The JavaScript can:

Read the file list of the logged-in user.

Upload files as the logged-in user.

Change file settings.

Show fake pages or redirect the user.

The session cookie is HttpOnly. So the JavaScript cannot steal the session token. This is not full account takeover. But it is still stored XSS on the main site. Any visitor can trigger it by opening a link.
